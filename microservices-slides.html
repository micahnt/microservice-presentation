Part 1

Introduction to Microservices & DDD

What microservices are, how to design them, and where to draw the lines

Architecture design journey

From one big application to many small units. Moving right, the pieces get smaller and the number of databases grows.

Which approach should we choose? It depends on your project.
  • Use a mixed architecture, and plan transitions between architectures as the system grows.
  • Martin Fowler and Sam Newman both recommend monolith first, then extracting services one by one.

What are microservices?

Small, independent services that work together to form one application.

Small & independent

Loosely coupled services that work together

Own codebase

Each one owned by a small team

Well-defined APIs

HTTP/REST, gRPC, or messaging

Independent deployment

Release one service without touching the others

Technology agnostic

Each service can use a different stack

Own database

Never shared with other services

"…an approach to developing a single application as a suite of small services, each running in its own process and communicating with lightweight mechanisms, often an HTTP resource API." — Martin Fowler

Benefits and challenges

Microservices don't remove complexity. They move it, from inside the code to between the services.

✓ Benefits
  • Agility and faster time-to-market
  • Independent scaling of each service
  • Small, focused teams
  • Small, separate codebases
  • Easy, independent deployment (CI/CD)
  • Right tool for each job (polyglot)
  • Resilience and fault isolation
  • Data isolation
! Challenges
  • Overall system complexity
  • Network problems and latency; chatty calls
  • Harder end-to-end development and testing
  • Data consistency (eventual consistency)
  • Deployment needs DevOps investment
  • Centralized logging and monitoring required
  • Debugging across many services is hard

When to use microservices, and when not to

Use them when you need
  • Independent deployment with zero downtime
  • Independent scaling of parts of the app
  • Different data stores per use case
  • Autonomous teams that own services
  • A really good reason (not hype)
Avoid them when
  • You would build a distributed monolith (the worst case)
  • You have no DevOps, CI/CD, containers, or monitoring
  • The team is small
  • The product is a brand-new startup with an unclear domain
  • Services would use a shared database (anti-pattern)
Distributed monolith = all the complexity of microservices, none of the benefits

Microservices design principles

Six principles that keep a microservice system from turning into a distributed monolith.

1 · Single responsibility

One service per business capability (Catalog, Basket, Ordering), not per technical layer

2 · Loose coupling, high cohesion

Change one service without changing others; related logic stays together

3 · Autonomy

Deploy independently and own your data (database per service)

4 · Well-defined contracts

Talk only through APIs and events: smart endpoints, dumb pipes

5 · Design for failure

Timeouts, retries, circuit breakers: one failing service must not take down the rest

6 · Automate & observe

CI/CD, containers, health checks, centralized logging

Based on Martin Fowler's microservice characteristics: componentization via services, business capabilities, products not projects, smart endpoints and dumb pipes, decentralized governance and data, infrastructure automation, design for failure.

Introduction to Domain-Driven Design (DDD)

Introduced by Eric Evans (Domain-Driven Design, 2003). Not a technology or framework, but a way to model software around the business.

Core idea: break a complex problem into smaller parts, and solve each one in its own model
Strategic DDD · the big picture
  • Understand and model the business domain
  • Find subdomains and bounded contexts
  • Define how they relate (context map)

→ Tells us where to split into microservices

Tactical DDD · inside one service
  • Design patterns for the code
  • Entities, value objects, aggregates
  • Domain events, repositories, domain services

→ Tells us how to build one service's model

Part 2

Synchronous Communication: REST & gRPC

Service-to-service calls where the caller waits for the answer

Service-to-service communication: sync vs. async

Services must cooperate: ask for data ("what's the discount?") or trigger work ("create the order").

Synchronous
ClientService
  • Client sends a request and waits for the response
  • HTTP/REST, gRPC, GraphQL, WebSocket
  • Request / response
  • Temporal coupling: both services must be up

EShop: Basket → Discount (gRPC) · Web → Gateway → APIs (REST)

Asynchronous
ProducerBrokerConsumer
  • Client sends a message and does not wait
  • AMQP via a broker (RabbitMQ, Kafka)
  • One-to-one (queue), one-to-many (pub/sub)
  • Loose coupling: the broker stores and retries

EShop: Basket → Ordering (BasketCheckout event)

Rule of thumb: REST for public APIs · gRPC for internal calls · messaging for workflows that span services

Introduction to Protobuf and gRPC

gRPC
  • Open-source RPC framework from Google
  • Runs on HTTP/2
  • Call a remote method as if it were a local object
Protocol Buffers (Protobuf)
  • Language-neutral contract in a .proto file
  • service = methods, message = data
  • = 1, = 2… are field numbers, not defaults
  • Compact binary: smaller and faster than JSON
  • .NET generates server base class and client
// Discount.Grpc/Protos/discount.proto
syntax = "proto3";
option csharp_namespace = "Discount.Grpc";

service DiscountProtoService {
  rpc GetDiscount (GetDiscountRequest)
      returns (CouponModel);
  rpc CreateDiscount (CreateDiscountRequest)
      returns (CouponModel);
  rpc UpdateDiscount (UpdateDiscountRequest)
      returns (CouponModel);
  rpc DeleteDiscount (DeleteDiscountRequest)
      returns (DeleteDiscountResponse);
}

message GetDiscountRequest {
  string productName = 1;
}

message CouponModel {
  int32 id = 1;
  string productName = 2;
  string description = 3;
  int32 amount = 4;
}

public class DiscountService(DiscountContext dbContext, ILogger<DiscountService> logger)
    : DiscountProtoService.DiscountProtoServiceBase
{
    public override async Task<CouponModel> GetDiscount(GetDiscountRequest request, ServerCallContext context)
    {
        var coupon = await dbContext.Coupons
            .FirstOrDefaultAsync(x => x.ProductName == request.ProductName)
            ?? new Coupon { ProductName = "No Discount", Amount = 0, Description = "No Discount Desc" };

        return coupon.Adapt<CouponModel>();
    }
    // CreateDiscount, UpdateDiscount, DeleteDiscount ...
}

// StoreBasketHandler.cs (Handle omitted)
public class StoreBasketCommandHandler(IBasketRepository repository,
        DiscountProtoService.DiscountProtoServiceClient discountProto)
    : ICommandHandler<StoreBasketCommand, StoreBasketResult>
{
    private async Task DeductDiscount(ShoppingCart cart, CancellationToken ct)
    {
        foreach (var item in cart.Items)
        {
            var coupon = await discountProto.GetDiscountAsync(
                new GetDiscountRequest { ProductName = item.ProductName }, cancellationToken: ct);
            item.Price -= coupon.Amount;
        }
    }
}

When to use REST, when to use gRPC

REST gRPC
Transport HTTP/1.1 or HTTP/2 HTTP/2
Payload JSON (text, human-readable) Protobuf (binary, smaller and faster)
Contract Optional (OpenAPI) Required (.proto), code is generated
Browser support Native Needs gRPC-Web or a proxy
Streaming Request/response only Client, server and bidirectional streaming
Easy to test by hand Yes: curl, browser, Postman Needs gRPC tooling (Postman, grpcurl)
Choose REST

Public APIs, browsers, third parties, simple CRUD

Choose gRPC

Internal, high-volume, low-latency calls between your own services

In EShop: REST behind the gateway for the web app · gRPC for Basket → Discount, once per cart item

Asynchronous Communication & Message Brokers

Events, brokers, and publish/subscribe

Basic event-driven architecture

The problem: chains of sync calls
GatewayShoppingCartProduct · Pricing
ShoppingCartOrderBilling · Shipping

Six calls for one click. Every service must be up, latencies add up, one slow service slows everyone.

The idea: publish events
  • An event is a fact that already happened, in the past tense: BasketCheckedOut, OrderCreated
  • The producer publishes it and moves on. It does not know who listens.
  • Consumers react in their own time

The role of a message broker (RabbitMQ)

ProducerExchangebindingQueueConsumer
What the broker does
  • Receives messages from producers
  • Stores them until consumers are ready, even if a consumer is down
  • Routes them to the right queues
  • Delivers and retries
  • Decouples services in time and location

MassTransit: .NET library on top of RabbitMQ that creates exchanges and queues and handles serialization and retries.

RabbitMQ: an open-source broker that implements AMQP.

Exchange Routes messages
Direct By exact routing key, to one queue
Fanout To all bound queues (broadcast)
Topic By routing-key pattern
Headers By message header attributes

Similar brokers: Apache Kafka, Azure Service Bus, ActiveMQ

Basic pub/sub pattern

Basket

Exchange

fanout

queueOrderingcreates the order · in EShop
queueNotificationsends an email · could be added

How it works
  • The publisher sends one message to an exchange (a topic)
  • The broker fans out a copy to every subscriber's queue
  • Subscribers work in parallel and independently
  • Add a subscriber without changing the publisher
  • A queue gives each message to one consumer; pub/sub gives every subscriber a copy
Watch out for
  • At-least-once delivery: consumers must be idempotent
  • No guaranteed order of messages
  • The broker is critical: run it highly available
  • Harder to debug and trace
  • Eventual consistency: the order appears a moment later

One extension method registers MassTransit + RabbitMQ
public static IServiceCollection AddMessageBroker(
    this IServiceCollection services,
    IConfiguration configuration, Assembly? assembly = null)
{
  services.AddMassTransit(config =>
  {
    config.SetKebabCaseEndpointNameFormatter();
    if (assembly != null)
        config.AddConsumers(assembly);   // consumers only

    config.UsingRabbitMq((context, cfg) =>
    {
      cfg.Host(new Uri(configuration["MessageBroker:Host"]!),
        host =>
        {
          host.Username(configuration["MessageBroker:UserName"]);
          host.Password(configuration["MessageBroker:Password"]);
        });
      cfg.ConfigureEndpoints(context);
    });
  });
  return services;
}

API Gateway & BFF

One front door for all clients, or one per kind of client

The role of an API Gateway

Without a gateway, every client must know every service's address, and every service handles auth, SSL and rate limiting itself.

1 · Gateway routing

Route each request to the right internal service (layer 7). Move a service: only gateway config changes.

2 · Gateway aggregation

Combine several service calls into one response

3 · Gateway offloading

Handle cross-cutting concerns in one place

Risk: a single gateway can become a bottleneck or single point of failure
Request flow through a gateway
Client

Request validation
IP allowlisting
Authentication / authorization
Rate limiting
Service discovery
Protocol conversion

Customer · Basket · Discount · Order

Pattern: Backends for Frontends (BFF)

One gateway per type of client, instead of one gateway for everyone.

Web appMobile appDesktop app
Web BFF gatewayMobile BFF gatewayDesktop BFF gateway
Microservices

Customer · ShoppingCart
Discount · Order

Why
  • Each BFF returns exactly what its frontend needs: a phone screen needs less data than a desktop page
  • Avoids one big gateway full of client-specific logic
  • Each frontend team can own and change its own BFF

Introduction to YARP (Yet Another Reverse Proxy)

YARP
  • Reverse proxy library from Microsoft, built on ASP.NET Core
  • Routes (what to match) and clusters (where to send)
  • HTTP/2, gRPC, WebSockets, load balancing, health checks, transforms
  • Plugs into ASP.NET Core middleware: rate limiting, auth

Summary

Microservices

Small, autonomous services built around business capabilities, each with its own data and deployment. Adopt them only for a real reason.

DDD

Where to split (bounded contexts, ubiquitous language)

Synchronous

REST for client-facing APIs, gRPC + Protobuf for fast, contract-first internal calls

Asynchronous

Events through a message broker (RabbitMQ + MassTransit) with pub/sub, for decoupled workflows

API Gateway & BFF

YARP or Ocelot as the single entry point; BFF when you have several kinds of clients
